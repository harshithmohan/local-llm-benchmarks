### Review round 1 → Stage 1
- Review prompt (verbatim, round 1): five severity-ordered findings, symptoms only. (1) Search results show unformatted timestamps — rows returned by a filtered search display the raw timestamp exactly as delivered by the server, with date, time, level and message running together, while the live tail shows a human-readable stamp; every row in the search view must show the same readable format as the live tail. (2) An entry arriving around a reconnect is lost — the replay replaces the stale tail correctly but the entry from the window does not appear afterwards; the fresh replay must replace the stale entries and any entry that arrived around the reconnect must still be shown, with nothing lost and nothing stranded above the replay. (3) Starting a search briefly shows old rows instead of a loading state — while the first search response is still held back the view shows existing live-tail rows rather than indicating a search is in progress; while the first filtered fetch is in flight the view must indicate loading and show no result rows, with the distinct empty state (plus a way to clear the filters) only once loading has finished with no matches. (4) Search text with surrounding whitespace is sent as-is — a padded term is sent wrapped as a substring search rather than trimmed; surrounding whitespace must be removed before sending, so ordinary text goes as a trimmed case-insensitive substring search, typed filter expressions still pass through as written, and blank input is not a search. (5) Scrolling up does not release the auto-follow — a genuine user scroll upward leaves the scroll-to-bottom lock engaged, the viewport jumps back to the bottom, and programmatic scrolling can re-engage a lock the user released; a genuine scroll away from the bottom must release the follow so the viewport stays where the user put it, and it must stay released until the user explicitly re-enables it.

### Review round 2 → Stage 2
- Review prompt (verbatim, round 2): five severity-ordered findings, symptoms only. (1) After the live connection drops and replays its backlog, stale entries from before the disconnect remain visible above the fresh backlog, and an entry arriving around the replay window can disappear instead of being kept, while new entries arriving after the replay do not consistently append after it; the fresh backlog must replace the now-stale entries, nothing arriving around the reconnect may be lost or duplicated, later entries must keep appending, and the rest of the view must stay consistent through the reconnect. (2) After activating a search string or level filters the view does not indicate that it is searching while the first fetch is in flight, so the pending state can read as empty or show the wrong content; while the first fetch is in flight the view must say it is searching or loading, visibly distinct from the empty-results state, which offers a way to clear the filters. (3) Through the disconnect and reconnect gap, before the fresh backlog arrives, the old tail stays on screen instead of indicating that fresh content is on the way; from the drop until the fresh backlog lands the tail must indicate that it is waiting or loading rather than presenting stale entries as current. (4) The header always shows the same title whether the page is showing the live tail or a server-backed search over the full history, with no count or mode hint; the header must tell the user which mode is showing, including how many entries are in the live tail versus indicating that the full server-side history is being searched. (5) Selecting the same set of level filters in a different order is treated as a different search, causing a fresh fetch instead of reusing the same results; the same set of active level filters must produce the same search regardless of selection order.
